MongoDB design for a chat app: four collections, ESR indexes, and an unread-count aggregation. I ran it against local `mongod` 9.0.2, on a throwaway instance in the P51 directory (port 27151, no auth). I seeded 5 users, 4 rooms, 11 memberships and 30,000 messages. The server is now stopped and its data directory deleted.

**Collections** (`$jsonSchema` validators are in `chat.js`)
- **`users`:** `{handle (unique), displayName, avatarUrl, createdAt}`.
- **`rooms`:** `{type: dm|group, name?, lastSeq: Long, lastActivityAt, lastMessage (small embedded snapshot)}`.
- **`memberships`:** `{roomId, userId, role, joinedAt, lastReadSeq: Long}`.
- **`messages`:** `{roomId, seq: Long, senderId, sender: {handle, displayName}, body, attachments[≤10], createdAt, editedAt?}`.

**Embed vs reference**
- **Messages are referenced.** They are unbounded, written constantly, and paginated, so embedding them in rooms would hit the 16 MB limit and force rewrites of a growing document.
- **Memberships are a separate collection, not an array in `rooms`.**
  - Each member's `lastReadSeq` changes independently and often. In an embedded array that would be a hot write on a shared room document.
  - Membership is queried from both sides: "members of a room" and "rooms of a user". A separate collection gives clean indexes for both, and group size is unbounded.
- **Embedded:**
  - `attachments` are owned by their message, read with it, and capped at 10 by the validator.
  - `rooms.lastMessage` and `messages.sender` are extended references: a few copied fields so the room list and chat view need no `$lookup`. The cost is stale `displayName` copies after a rename.
- **Per-room `seq`:**
  - Messages get a per-room counter via `findOneAndUpdate({$inc: {lastSeq: 1}})` on the room document.
  - It makes read positions exact integers, which is why unread is a range on `seq`.
  - The cost is that each room's counter document becomes a write hotspot. That is fine for chat-scale rooms but would not suit very hot broadcast rooms.

**Indexes**
- **`messages {roomId:1, seq:-1}` (unique):**
  - Equality on `roomId`, then sort and range on `seq`, which is the ESR rule.
  - One index serves history pagination (`seq < cursor`, sorted descending) and the unread range (`seq > lastReadSeq`).
- **`memberships {roomId:1, userId:1}` (unique):** members of a room.
- **`memberships {userId:1, roomId:1}`:** rooms of a user.
- **`users {handle:1}` (unique):** lookup by handle.

**`explain` results** (all use an index scan, none needs a blocking sort)

| Query | Index | Returned / keys / docs examined |
|---|---|---|
| History page, limit 50 | `roomId_1_seq_-1` | 50 / 50 / 50 |
| Unread range with `senderId != me` | `roomId_1_seq_-1` | 9 / 10 / 10 |
| Memberships of a user | `userId_1_roomId_1` | 4 / 4 / 4 |
| Members of a room | `roomId_1_userId_1` | 5 / 5 / 5 |
| User by handle | `handle_1` | 1 / 1 / 1 |

The `$lookup` inside the unread pipeline used `roomId_1_seq_-1` with no collection scans.

**Unread aggregation** (`unreadPipeline` in `chat.js`)
1. `$match {userId}` on `memberships`.
2. `$lookup` into `messages` with `let {rid, lr}`, matching `roomId == rid` and `seq > lr`, then `senderId != me`, then `$count`.
3. `$project` the count (0 if none), keep only rooms with `unread > 0`, `$lookup` the room name, and sort by `lastActivityAt` descending.

For user "ana" (the first seeded user):
- **general:** 9 unread.
- **dev:** 5,193 unread.
- **dm and empty:** 0, so they are dropped.

A separate `countDocuments` per room gave the same numbers for all four rooms.

**Caveats**
- **Unread cost grows with unread messages:** the `$lookup` examines every unread message, including a `senderId` filter on fetched documents (7,910 documents examined here, mostly the dev room). Cap the count (for example `$limit 100` and show "99+") or use `room.lastSeq - lastReadSeq` for an O(1) approximation that includes your own messages.
- **My own messages:** the `senderId` filter excludes your own messages from the exact count. Advancing the sender's `lastReadSeq` when they post would make the filter unnecessary.
- **Validator codeName:** the validator rejected an int `seq` as intended, but the printed `codeName` was empty. I did not investigate why.
- **Shutdown not confirmed by process listing:** `pgrep` was blocked by the sandbox, so I confirmed shutdown only by a failed reconnect on the port.
