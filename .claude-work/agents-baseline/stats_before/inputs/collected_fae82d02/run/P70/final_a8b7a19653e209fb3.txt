RESULT: I built a small FastAPI app in the scratch dir that stores passwords with argon2id and issues rotating opaque session tokens. 30 tests pass (`uv run pytest`).
- **Password storage:** argon2-cffi forced to argon2id with m=64 MiB, t=3, p=4 (the RFC 9106 second profile). Old hashes are re-hashed at the next login if the settings change. Passwords over 1024 bytes are rejected without being hashed. When the username doesn't exist, the login still runs one full argon2 check against a dummy hash made with the same settings, and returns the same 401 body and headers as a wrong password.
- **Tokens:** each token is `selector.verifier`. The server looks it up by the random selector, stores only SHA-256(verifier), and compares with `hmac.compare_digest`. An unknown selector or malformed token still does one comparison, against a dummy digest. Access tokens last 15 min and refresh tokens 14 days. Every refresh issues a new access and refresh token and retires the old access token. Each login starts its own session ("family").
- **Reuse:** if an already-used refresh token comes back with the correct secret part, the whole session is revoked, including the newest tokens of the legitimate user. A guessed secret paired with a known selector cannot trigger that revocation, so knowing a selector is not enough to log someone out. Two refreshes racing on the same token: exactly one succeeds. Logout revokes the session.

EVIDENCE: Passed: 30/30 tests, five runs in a row with no flakes; `ruff check` clean (run temporarily via `uv run --with ruff`). Each key check was broken on purpose (the code edited, the tests run, then restored) to confirm the tests catch it:
- Using `==` instead of `compare_digest` fails 8 tests (`test_token_checks_always_use_compare_digest[*]`).
- Removing the session revocation on reuse fails `test_refresh_token_reuse_rejected_and_family_revoked` and `test_concurrent_refresh_only_one_wins`.
- Not marking a refresh token as used fails the same 2 tests.
- Removing the dummy check for unknown users fails `test_unknown_user_runs_a_full_argon2_verify` and `test_unknown_user_timing_matches_wrong_password`.

The timing test compares median login times and expects unknown-user/wrong-password between 0.5 and 2. A negative-control test (`test_timing_check_detects_a_missing_dummy_verify`) shows the ratio drops below 0.2 without the dummy check.

Not done: no independent security-auditor review. This is a new auth design, which would normally call for one; I skipped it because it is scratch demo code. Starlette warns that using httpx with its TestClient is deprecated (suggests httpx2); harmless here.

Residual risk:
- Users and sessions live in memory under one lock: no persistence, and it only works as a single process.
- No rate limiting or lockout, and each failed login costs 64 MiB of memory, so the login endpoint is open to brute force and resource exhaustion.
- `/register` returns 409 for a taken username, which reveals which accounts exist.
- Tokens travel in the request body and Bearer header, and HTTPS is assumed.
- The timing test measures in-process timing with cheap test settings, not network-level timing.
