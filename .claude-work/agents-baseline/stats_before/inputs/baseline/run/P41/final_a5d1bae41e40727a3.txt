**GOAL.** Replace the cron jobs of the 3-service Python monolith with a queue plus workers. Each scheduled slot must run exactly once and be observable. Each job moves over without downtime and can be rolled back on its own.

**CONTEXT**
- The current workspace (`/Users/pmrj/ZDone/Worktree_for_Claude/claude-agent-stack/agents-workflow-token-optimization-573fd0`) is the agent-stack repo, not the monolith. No crontab, Celery or APScheduler code is here. I don't know the monolith's path, database, deploy target or framework (see QUESTIONS).
- Procrastinate (Postgres-backed): every worker schedules periodic tasks, and the database makes sure each period is deferred only once. Periodic scheduling therefore survives as long as one worker is up. A task more than 10 minutes late is skipped by default (configurable). The task receives the slot `timestamp`. Source: https://procrastinate.readthedocs.io/en/stable/howto/advanced/cron.html
- Celery 5.6.3 (current stable): "You have to ensure only a single scheduler is running… otherwise you'd end up with duplicate tasks." Source: https://docs.celeryq.dev/en/stable/userguide/periodic-tasks.html
- The Redis broker's visibility timeout defaults to 1 hour. A task not acknowledged by then is handed to another worker and runs again. Source: https://docs.celeryq.dev/en/stable/getting-started/backends-and-brokers/redis.html
- Things cron gives for free that the new system must reproduce explicitly: host timezone, `MAILTO` alerting, overlap behaviour (`flock` or none), working directory, environment, host-local files.
- EU daylight saving time ends Sunday 2026-10-25 (01:00–01:59 repeats in Europe/Lisbon). That date falls inside a likely cutover window.

**OPTIONS**

| | A. Postgres queue (Procrastinate) | B. Redis + Celery 5.6 (beat) | C. Temporal |
|---|---|---|---|
| Pros | No new infrastructure if Postgres is the main DB. Periodic scheduling is deduplicated in the DB and highly available. Enqueue can share the app's transaction. Job state can be queried with SQL. | Most mature option; routing, canvas, Flower; widely known. | Durable execution, per-step retries, schedule overlap and catch-up policies (unverified). |
| Cons | Adds load and connections on the primary DB. Smaller ecosystem. Throughput ceiling, though fine at cron scale. | Beat must be a singleton. Tasks running longer than the 1 h visibility timeout get duplicated. Redis persistence must be configured. New infrastructure if Redis isn't already run. | Heavy platform (server, persistence or Cloud bill), determinism constraints, learning curve. |
| Cost/risk | Low | Medium | High |

Decision rule, applied at step 2:
- **A** if Postgres is the primary DB and jobs run at cron scale (well under ~100 enqueues/s).
- **B** if Redis or Celery is already operated.
- **C** only if the inventory shows multi-step jobs lasting hours that need compensation on partial failure.

The rest of the plan works with any of them. The safety mechanism (the `job_runs` claim below) doesn't depend on the backend.

The core mechanism is a slot claim table in the app DB, used by both the legacy cron path and the worker:
```sql
CREATE TABLE job_runs (job text, slot timestamptz, executor text, status text,
  attempt int DEFAULT 1, started_at timestamptz, finished_at timestamptz, error text,
  PRIMARY KEY (job, slot));
INSERT INTO job_runs (job, slot, executor, status, started_at)
VALUES ($1, $2, $3, 'claimed', now()) ON CONFLICT DO NOTHING RETURNING 1;
```
- Whoever gets the row runs the job. Everyone else exits 0 and logs "claimed by X".
- Retry reclaims the row with `UPDATE … WHERE status='failed' OR (status='claimed' AND started_at < now() - timeout)`.
- Slot = the latest cron tick at or before now, in the job's explicit timezone (`croniter`, with 1 s tolerance).

**RISKS**
1. **Duplicate runs** (at-least-once delivery, two schedulers, cron and worker overlapping during cutover). Mitigation: the `job_runs` primary key, idempotency keys on external side effects, a singleton or DB-deduplicated scheduler.
2. **Long tasks redelivered** (Redis visibility timeout of 1 h, deploy kills). Mitigation: chunk R3 jobs, timeout below the visibility timeout, graceful drain, reclaim only after the timeout.
3. **Lost runs** (scheduler down, Procrastinate's 10-minute late skip). Mitigation: explicit misfire policy per job and a dead-man alert on missing slots.
4. **Hidden cron assumptions** (timezone, working directory, env, host files, `MAILTO` as the only alerting). Mitigation: inventory columns plus the step 7 baseline before any behaviour changes.
5. **DB pressure** from worker concurrency or queue tables. Mitigation: per-queue concurrency caps, pool budget, data-engineer review.
6. **Import side effects** when workers load the web app. Mitigation: the dedicated worker bootstrap, tested by importing every task module in CI.
7. **DST behaviour differs between cron and the new scheduler.** Mitigation: explicit timezone per job, frozen-clock tests for 2026-03-29 and 2026-10-25, prefer UTC for jobs that aren't tied to business hours.

**VERIFY**
- Exactly-once per slot: `SELECT job, slot FROM job_runs WHERE status='succeeded' GROUP BY 1,2 HAVING count(*) <> 1` returns 0 rows.
- No missing slots: for every expected slot (from croniter) in the window there is a `succeeded` row within the grace period. Disabling one job in staging makes the missed-slot alert fire.
- Output parity against the cron baseline: affected-table row counts and checksums, and counts of emails and API calls, for the same slots.
- Fault drills in staging, each followed by one success per slot:
  - SIGKILL a worker mid-task
  - restart the broker or DB
  - kill the scheduler leader (B)
  - deploy during a run
- Latency: p99 enqueue lag under 30 s and start lag under 60 s for the default queues (thresholds to confirm).
- Rollback drill: re-arm cron for one job and disable its periodic task; the next slot is claimed by `cron`.
- Security: no pickle in the config, and no secrets in serialized args (grep the queue payloads).
