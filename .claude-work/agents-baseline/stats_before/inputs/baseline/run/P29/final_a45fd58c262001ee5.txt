I implemented offline orthogonal range counting in C++20, running in O((n+q) log n) time and O(n+q) memory, and stress-tested it against a brute force with no mismatches. I read "dynamic-connectivity-free" as a fixed set of points with all queries known up front and no updates; interleaved updates would need CDQ divide and conquer at O((n+q) log² n), which misses the requested bound.

**Usage.** The input is `n q`, then n lines `x y`, then q lines `x1 y1 x2 y2`, all int64. The output is one count per line. Rectangles include their edges, a rectangle with x1 > x2 or y1 > y2 is empty, and duplicate points are each counted. Malformed input exits with status 1 and a message.

**Insight.**
- Sort the points by x. The points with x < x1 are then the first a of them, and those with x ≤ x2 the first b, where a and b come from two binary searches.
- So answer = G(b) − G(a), where G(k) counts how many of the first k points have a y-rank in [lo, hi).
- The 2q events go into n+1 buckets by counting sort, and one sweep with a Fenwick tree over y-ranks answers them all.
- Queries are never sorted, so the per-query cost is log n, not log q.

**Correctness.**
- When bucket k is answered, the tree holds exactly the first k points; this follows by induction on k.
- A point's y lies in [y1, y2] exactly when its rank lies in [lower_bound(y1), upper_bound(y2)).
- The check "a ≥ b or lo ≥ hi, answer 0" is required: on an inverted rectangle the difference would go negative.
- Coordinates are only compared, never offset, so the full int64 range is safe. Counts are at most n < 2³¹.

**Cost.** Sorting is O(n log n), each rectangle needs four O(log n) binary searches, bucketing is O(n+q), and each Fenwick step is O(log n).

**How it was verified.**
- **Brute-force stress test (`stress.cpp`):**
  - every set of up to 4 points on a 3×3 grid against all 625 rectangles with corners in {−1..3} (4.6M checks);
  - 3.4M random small instances over 5 seeds, covering heavy ties, int64 extremes, edges on or one off a point coordinate, inverted and degenerate rectangles;
  - about 1,000 medium instances (n, q ≤ 3000);
  - two n = q = 2·10⁵ instances, with 4,000 answers each re-counted by brute force.
  
  It also runs clean under ASan, UBSan and hardened libc++.
- **End-to-end (`test_e2e.py`, hypothesis):** on 1,500 generated inputs the program's output equals both a Python oracle and the brute-force program. 9 valid and 20 malformed fixed inputs also pass, including NUL bytes, glued tokens, overflow and a maximal header.
- **Full scale (`make fullcheck`):** output is byte-identical to the brute force on all 2 × 200,000 answers (uniform and heavy-ties data). The brute force takes about 68 s per instance.
- **Seeded bugs:** all 11 deliberately introduced bugs were caught, among them boundary off-by-ones, the missing empty-rectangle check, 32-bit truncation and comparing coordinates as doubles. A 12th change had no effect on results, so there was nothing to catch.
- **Speed (algorithm only, median of 5):**

| n = q | time | ns per (n+q)·log₂ n |
|---|---|---|
| 5·10⁴ | 14.1 ms | 9.0 |
| 2·10⁵ | 68 ms | 9.7 |
| 8·10⁵ | 367.5 ms | 11.7 |
| 1.6·10⁶ | 1,049 ms | 15.9 (data no longer fits in cache) |

  With n = 1000 and q = 1.6·10⁶ it takes 131 ms (8.2 ns), which supports the log n per-query cost. The whole program, reading and writing included, runs in 0.09–0.14 s at n = q = 2·10⁵ (12 MB input).
- **Independent review:** a code reviewer found no correctness defects, and I fixed its four findings:
  - environment `CXXFLAGS` silently dropped `-std=c++20`;
  - `-D_GLIBCXX_ASSERTIONS` was missing from the sanitizer flags;
  - the input buffer stayed in memory while the counting ran;
  - several input edge cases were untested.
  
  Everything was re-run and passes.
- **Verifier:** a hook blocked it from building or running anything. It could only read the code and run a line-by-line Python port of the algorithm (20,000 instances, 0 mismatches), so no independent agent has re-executed the tests.
