# Schema migrations
Hub: `db-design`. Engine-specific safe DDL: `postgresql` (Migrations without downtime), `mysql` (online DDL), `sqlite` (ALTER limits and the 12-step rebuild), `mongodb` (schema versioning, validators).

## Rules
- Migration tools: follow the repo (Alembic, Flyway, Liquibase, sqlx, dbmate, Prisma, Atlas, sqitch, Django/Rails migrations). One migration per logical change, committed with the code that needs it, never edited after it ran anywhere shared.
- Every migration reversible (a down migration or a written forward-fix plan) and tested on a copy with production-like volume: time it, and watch the locks it takes.
- Running against production, or any database you don't own, is the user's decision: show the SQL, its expected locks and duration, and the rollback, then wait.
- Autogenerated migrations (`alembic revision --autogenerate`, ORM diffs) are drafts: read every statement; renames come out as drop + add and lose data.

## Expand/contract (zero-downtime changes)
Code and schema deploy separately, so every intermediate state must work with both the old and the new code.
1. **Expand:** add the new column/table/index (nullable or with a constant default; indexes built online).
2. **Dual write:** the app writes old and new.
3. **Backfill** in batches (bounded by primary-key ranges, a few thousand rows per transaction, sleeps between batches, resumable, idempotent); monitor replication lag and locks.
4. **Switch reads** to the new shape; verify with counts and checksums.
5. **Contract:** stop writing the old shape, then drop it in a later release.
Use it for renames, type changes, splitting or merging tables, and moving data between stores.

## Locks and timeouts
- Set a lock timeout and a statement timeout in every migration session, and retry rather than queue behind a long query while blocking everyone (PostgreSQL `SET lock_timeout`; MySQL `lock_wait_timeout`).
- Long-running transactions and replicas block or lag DDL: check for them first.
- Separate fast metadata-only DDL from data rewrites; never put a backfill and a schema change in one transaction on a large table.

## Testing migrations
- CI applies all migrations from empty and checks the result equals the declared schema (no drift); then applies down/up once.
- Lint migrations where a linter exists (e.g. Squawk for PostgreSQL, Atlas migration lint; unverified as of 2026-10-02 — check each tool's docs).
- Data migrations get a test with fixture rows covering NULLs, duplicates and edge values.

## Verify
- [ ] Migration ran on a production-sized copy; duration and locks recorded.
- [ ] Rollback (down migration or forward fix) exercised once.
- [ ] Old and new application versions both pass their smoke tests against the expanded schema.
- [ ] Backfill counts/checksums match between old and new shapes before contract.
